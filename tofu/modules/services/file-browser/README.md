# file-browser (drive.wvl.app)

FileBrowser Quantum on mindy. Six sources: `audio` and `audio-archive` still
arrive over NFS from samson, the four document shares are local on `rafiki`
since 2026-09-18.

## What is in code and what is not

`config.yaml` is generated in `main.tf` and uploaded into the container. It
carries the source list, OIDC settings, and the defaults applied to new users.

`database.db` is not, and cannot be. It holds users, their per-source **scopes**,
share links and access rules. Nothing in this module can reach into it.

Three settings here reach into that database, and they do **not** behave alike.
All three were read off the v1.5.6 source, because upstream documents none of
them:

| Setting | Reaches existing users? | Where |
|---|---|---|
| `sources[].default_enabled` | **yes**, every startup | `cmd/user.go` → `updateUserScopes` |
| `auth.adminPassword` | **yes**, every startup | `cmd/user.go` → `validateUserInfo` |
| `user_permissions` | **no**, at creation only | `updatePermissions` returns early on `user.Version >= 1` |

`updateUserScopes` walks every user on startup and grants a scope for any
`default_enabled` source they lack, so flipping one to `true` hands it to
everyone on the next container start — existing accounts included. This is the
opposite of what the OIDC path suggests: `ApplyUserDefaults` there runs only in
the auto-create branch, which is easy to read as the whole story. It is not.

`user_permissions` genuinely is creation-only. `updatePermissions` is a one-time
migration off a deprecated `Perm` field, not a sync, and it bails immediately for
any user at version ≥ 1. To change an existing person's permissions, edit them in
the admin UI, or delete the user and let OIDC recreate them.

Admin does **not** bypass scopes. An admin with no scopes sees no files; the
admin flag gates the `/api/users` endpoints, not source visibility.

## The admin account

`auth.adminPassword` is generated by `random_password` in this module and written
back into filebrowser on every start. Read it with:

```
tofu output -raw filebrowser_admin_password
```

A password changed through the UI does not survive a restart — the config wins.
That is deliberate: the alternative is an admin credential nobody has, which is
exactly how this account became unusable on 2026-09-18. Recovering it otherwise
means stopping the container (Bolt takes an exclusive lock, and the CLI aborts
with *"the database is locked"*) and running `filebrowser set -u` from a one-off
container with a hand-written config.

## Why the config is uploaded outside the config directory

To `/home/filebrowser/config.yaml`, not into `config_path`.

`config_path` is a bind mount. **A bind mount shadows an upload to the same
path**: the uploaded file lands in the image layer and the mount hides it, so
filebrowser reads whatever stale copy is on the host. No error is raised
anywhere. Uploading beside the mount instead keeps the generated file visible.

`server.database` is set explicitly for the same class of reason. The database
path resolves relative to the config file, so moving the config without pinning
the database risks filebrowser creating a fresh empty one and abandoning the
real users.

## Why the container needs group 100

Every share is `root:100`, mode `2770` — nothing for "other". The image runs as
uid 1000, whose only group inside the container is 1000.

Over NFS that was enough: the client sends the uid and **samson** answers the
ACCESS call using the groups it resolves for uid 1000, which include 100. On a
local filesystem the kernel uses the container's own `/etc/group`, finds only
group 1000, and denies. Same uid, same mode, different answer — which is why the
document migration broke access without changing a single permission bit.

`group_add = ["100"]` restores it. The setgid bit on those directories keeps new
uploads in group 100, so it stays sufficient.

Seven directories are `755 root:100` (for example `gezin-officieel/Aankopen`).
Group 100 can browse but not write into them. That was equally true over NFS.

## Adding a share

1. Add the directory name to `local.document_shares` in `../../../main.tf`.
2. Add a matching entry to `sources` in the same file.

Skipping step 2 mounts the directory and leaves it unreachable, because
filebrowser only serves paths listed in `server.sources`. A `precondition` on
the container fails the plan instead.
